# Hope Writing Rules · v2.0

How Hope writes anything that goes out in the user's name: emails, LinkedIn messages, cover letters, form answers, replies to recruiters, follow-ups. These rules come from a real job hunt, learned by comparing what the AI drafted with what the person actually sent. The goal is a draft the user can send without editing.

Examples use the test persona Jane Doe: Senior Product Designer at Figma, Brooklyn. Before that, Linear (2019 to 2022) and independent client work (2017 to 2019).

**Which source wins:**

1. The user's own samples and learned patterns in `applications/_common/my-voice.md`. Where they disagree with this file, `my-voice.md` wins.
2. This file.
3. `references/voice-guide.md`, which is Hope's own voice in chat, not the user's.

**Read before drafting:** `applications/_common/my-voice.md`, `HUNT-PROTOCOL.md` (the canon and "My rules"), `applications/_common/profile.md`, the role's `JD.md` if there is one, the "What you have told them" section of the role's `APPLICATION-ANSWERS.md`, any `sent-*.md` files in the role folder, and the whole thread you are replying to.

## 1. The target and the read-aloud test

Read the draft aloud.

- If it sounds like **a confident person talking about work they enjoy**, it is right.
- If it sounds like **a careful person building an argument**, rewrite it.

Write to be spoken. Short sentences. Contractions are fine. When in doubt, cut.

## 2. Rules for every message

1. **Answer the question that was asked.** Not the nearby question the user could answer better. "What excites you about this role?" gets what excites them, not a list of their experience.
2. **Every fact is traced before it goes in.** Numbers, dates, names, titles and outcomes come from the canon in `HUNT-PROTOCOL.md`, `career-graph/career.json`, `applications/_common/profile.md`, or the user's words in chat. Not on file: ask. Every duration is computed (`references/failure-patterns.md`, lesson 14).
3. **Specifics over vague.** Replace a vague amount with a number, a date or a scale from the canon. "A lot of teams" becomes "12 product teams". If the canon has no number, ask for one. Never invent one.
4. **Write what happened, not a modest version of it.** Before: "I helped with the design-system work." After: "I led the consolidation of Figma's design system across 12 product teams." Not boastful either. Just what happened.
5. **Full stops over semicolons.** Before: "I prototype fast; the first version is rarely the last." After: "I prototype fast. The first version is rarely the last." Semicolons read as written. Full stops read as spoken.
6. **No flattery, no mirroring.** Never quote a company's values or posting back at them to show you read the page. Quote them only to argue with a point or add something they do not know.
7. **Do not open with the clever line.** Open with a plain statement. Let the memorable line land at the end of the first paragraph, once the reader is listening.
8. **Stop at the strongest line.** Never add a weaker "one more thing" sentence after the best ending.
9. **Volunteer the awkward adjacent fact.** If leaving a fact out would make the answer quietly misleading, put it in, plainly, and move on. This is about a fact sitting next to a claim the user is making. A skill nobody asked about is not adjacent to anything (see section 4).
   - Question: "Have you used Framer?"
   - Answer: "Yes. I prototyped Linear's mobile onboarding in Framer. We later moved prototypes into Figma, because that's where the engineers already reviewed work."
10. **No self-undermining sentences.** State what the user has. Never narrate what they lack. See section 4.
11. **Never narrate the message inside the message.** No "I'm writing to you because…", no "You asked for a short note, so…", no "so you hear it from me first". The reader can see what the message is doing.
12. **Never re-ask what the form already asks.** A closing line offering to "share more about why I want to join" is dead weight when the form has that question.
13. **Plain English.** See the table in section 5. Keep real technical terms.
14. **No em dashes.** See section 6.
15. **Never expand a name beyond the source.** See section 7.
16. **No client names and no internal project names** from the user's employer (hard rule 8). Describe the work by what it does.
17. **Read the whole thread first.** Before drafting a reply, read the whole thread, including what the user last sent. Read it again right before handing the draft over: they may have replied in the meantime. Never repeat what the user already told them (hard rule 17).
18. **Dictated notes are raw material.** When the user talks or dictates, rewrite it in the register of the document. Never paste spoken phrasing into a résumé, letter or form answer. Dictated: "so basically I was the one who got all twelve teams onto one system, took like eight months." In a résumé: "Led the consolidation of Figma's design system across 12 product teams in 8 months."
19. **Reuse what is approved.** When an approved letter or answer exists, reuse its wording word for word and change only the focus. Do not rewrite text the user already said yes to.
20. **Keep the user's own draft as the base.** When the user hands over their own draft, edit it lightly. Keep their opening and their voice. Show the changes as a table first (hard rule 15).
21. **Every draft about a role starts with the role.** The draft header carries the posting link and the role folder path (hard rule 16; header shape in `references/hunt-folder.md`, section 5.5).
22. **Stay consistent with what the user has told them.** Check the "What you have told them" section of `APPLICATION-ANSWERS.md`. A new message must not contradict it. Everything in it must still be true.

### Peer, not desperate

Every message reads as a peer with options, not a candidate asking for a favour.

1. **One follow-up, then wait.** After one nudge, the next move is theirs.
2. **Never ask about their timeline twice.**
3. **Do not propose the next call for them.** Ask what the next step is. Let them set it.
4. **Say less rather than more.** A short message reads as confident. A long one reads as anxious.
5. **Never put negotiation plans in writing.** Pay strategy, other offers, a walk-away number: none of these go in a message or email. Do not volunteer pay in writing. If a recruiter asks in writing, use the written phrasing in `profile.md`, section 3, and nothing more. The rest waits for the call.

- Before (a second nudge, a week after the first): "Just following up again! I'd love to hear about timing, and could we set up a call this week or next?"
- After: no message. It is their turn. Hope sets a reminder for the user instead, if they want one.

## 3. The shapes

### 3.1 Email to a hiring team

Use it for apply-by-email roles and cold emails to a team.

```
Hi <Company> hiring team,

I'm a <city>-based <current title>, currently at <employer>, <N> years in <field> and the last <M> of them <the thing that matters to this role>. Résumé attached.

Something I've built:

<The story. One piece of work: what the user did and what changed, with a number from the canon.>

<One paragraph on the idea in their posting that made the user want to write. In the user's words, never the posting's.>

<Only if a hard gate applies: one plain paragraph that leads with the yes. Otherwise leave this out.>

<A warm close, for example: "I'd love to talk.">

<Sign-off from my-voice.md>
<First name>
```

The rules that make it work:

1. The first paragraph makes the fit claim and nothing else: city, title, employer, years. Then "Résumé attached." and stop. The résumé carries the rest.
2. Compute N and M with the lesson 14 check in `references/failure-patterns.md`. If M cannot be made true, drop "and the last M of them…".
3. "Something I've built:" on its own line is the whole transition. Do not explain what the email is doing.
4. One belief paragraph, aimed at one specific idea in their posting.
5. A gap paragraph only for a hard gate (section 4). A missing nice-to-have never goes in.
6. Warm, not formal. The sign-off and signature come from `my-voice.md`.

**Jane Doe example:**

```
Hi Northwind hiring team,

I'm a Brooklyn-based Senior Product Designer, currently at Figma, nine years in product design and the last four of them leading a design system across 12 product teams. Résumé attached.

Something I've built:

At Figma I led the consolidation of our design system across 12 product teams. In 8 months we unified 37% of the product surface, and onboarding time for new designers dropped from 3 weeks to 1.

Your posting says engineers should want to use the design system, not be told to. That's the part I care about most. People trust a system they helped shape, which is why I built the proposal and voting flow before the components.

I'd love to talk.

Thanks,
Jane
```

The durations were computed: June 2017 to October 2026 is 9 years 4 months; September 2022 to October 2026 is 4 years 1 month.

### 3.2 First reply to a recruiter or agency

**The first-contact rule:** surface hard blockers early. Never volunteer a missing nice-to-have.

| Say it in message one | Keep it for the call, or never |
|---|---|
| A sponsorship need (a real gate; finding out late wastes everyone's time) | Any preferred qualification the user lacks |
| Location, if the role is onsite somewhere the user will not go | Depth in a tool the user has not used |
| A travel limit the role would break | Anything the posting lists as "nice to have" |
| A timeline, when the user has one. With agency recruiters it helps them. | |

- **Agency recruiters:** do not ask about pay in message one. They bring the band to the intro call anyway, and asking before any relationship exists reads as transactional.
- **In-house recruiters:** pay is the point of their screen. If they ask, use the written phrasing in `profile.md`, section 3.
- **Show you read their message**, in a few words: "the AI platform side especially". Everything beyond that is padding.
- **Close with the filter:** "If this matches your hiring needs and timeline, let's chat." It asks them to check themselves against the user's constraints. It is a filter, not an offer. Keep it.

```
Hi <first name, exactly as they signed>,

Thanks for reaching out about <role>. <A few words that show the user read their message.>

<One or two lines on the fit, from the canon.>

<Hard blockers only, leading with the yes. Leave this out if there are none.>

If this matches your hiring needs and timeline, let's chat.

<Sign-off from my-voice.md>
<First name>
```

**Jane Doe example** (an agency recruiter, Pat, about a role that needs frequent travel):

```
Hi Pat,

Thanks for reaching out about the Senior Product Designer role, the AI platform side especially.

I lead design-system work at Figma across 12 product teams, and before that I designed Linear's keyboard-first command palette.

I'm in Brooklyn, and I can travel up to a quarter of the time.

If this matches your hiring needs and timeline, let's chat.

Thanks,
Jane
```

Cut from an earlier draft: "I should mention I haven't designed for an AI product before" (a nice-to-have, not a gate) and "What's the salary range?" (an agency; it comes on the call).

### 3.3 Cover letter

The shape is fixed. Only the first paragraph changes from company to company.

```
Hi <Company> team,

<Paragraph 1: THE PART THAT CHANGES. One story, chosen for this reader: a decision the user made and what it changed, with a number from the canon. At most one sentence connects it to this company. Never praise.>

<Paragraph 2: the shape of the user's days. What they do, who with, how the work moves. Same text in every letter.>

<Paragraph 3: how the user works and what they care about. Same text in every letter.>

<The personal line from my-voice.md, word for word. Leave it out if the user has none.>

Would love to talk with the team.

<Signature block from my-voice.md>
```

Rules:

1. **Length:** about 300 to 360 words of body. Check with `wc -w cover-letter.md`, then subtract the header and signature.
2. **Never add a "practical notes" paragraph.** No location, relocation, visa, pay or availability. The form asks those. The call handles the rest.
3. **Paragraphs 2 and 3 are the same in every letter.** The first time the user approves a cover letter, save it in `my-voice.md` under "Samples" as "Cover letter (approved)". Copy paragraphs 2 and 3 from there every time.
4. **One sentence of company relevance, never a paragraph.** The letter says who the user is. It does not argue that the company is right.
5. **Two live applications at one company:** the letters are identical except paragraph 1. The same recruiter may read both. Tailoring is expected; claiming exclusivity is fatal. Check the set:

```bash
grep -rniE "only (version|role|job)|all I want|what I really want|nothing else" applications/northwind-*/cover-letter.md
```

It must print nothing.

**Jane Doe example of paragraph 1, for two companies:**

- For a developer-tools company: "At Linear I designed the keyboard-first command palette. It is still in production, and power-user retention rose 18% in the group that adopted it. Most of what I design is for people who would rather never touch a mouse."
- For a company building a design system: "At Figma I led the consolidation of our design system across 12 product teams. In 8 months we unified 37% of the product surface, and onboarding time for new designers dropped from 3 weeks to 1."

### 3.4 "Why us?" answers

The answer is about the user, not the company.

- **The shape:** what the user likes doing · what they want to be doing next · optionally, what is new to them here and why that is the draw.
- It may name one real thing about the company that the user has actually used or done. One sentence.
- No mirrored posting language. No flattery. Research belongs in the interview, where it can be a conversation. In a text box it reads as courtship.
- Never pay. "Why us?" and "Why are you leaving?" are different questions (section 3.6).
- Artifacts and numbers are optional here. The résumé carries them.

**Jane Doe example:**

- Before: "Northwind's mission to make AI tools feel like craft tools resonates deeply with me, and your commitment to design excellence is exactly what I'm looking for."
- After: "I like building the parts of a product other designers build on. That means type, components, and the rules for how they change. I want to do that for AI tools next, where nobody has settled what the components even are yet. I use Northwind's editor every week for my book layouts, so I already know where it fights me."

### 3.5 "What are you like?" questions

When a question asks what the user is like (working style, working with engineers, client-facing work), lead with a behaviour or a preference, not a résumé number. Save numbers for questions about what they did. Every applicant has a number. Very few say what they are like in the room.

**Jane Doe example:** "Tell us about working with engineers."

- Before: "I led a design system used by 12 product teams and cut onboarding from 3 weeks to 1."
- After: "I like to sketch the first version with the engineer in the room, not hand over a finished file. Most of my best decisions started as their first question."

### 3.6 "Why are you leaving?"

- Short and true. Use the answer in `profile.md`, section 7.
- Never add a second reason the user has not approved for writing. Personal reasons are theirs to raise, in their own words, if and when they choose.
- If the user chooses to put their leaving reason inside a "why us" answer: warm half first, then the honest half. Say once that this has a cost at the application stage. Record their decision in `HUNT-PROTOCOL.md` under "My rules", then do not raise it again.

### 3.7 "Tell me about a time you disagreed…" answers

1. State the other person's position fairly, with their reason.
2. Say the user saw it differently, and sat down with them. Never escalating, never going around them.
3. Give the actual argument in one or two sentences.
4. Show the data: the comparison the user ran, the numbers it gave.
5. Leave the other person a fallback, so nobody has to lose.
6. End on the joint decision, not on the user winning.

About 150 to 200 words, one block, no headings. A question that asks for a failure gets a real one, told straight. That is answering the question, not undermining the user.

### 3.8 Short messages

These are a few lines each. The goal is to keep things moving, not to restate anything.

| Message | The shape | Jane Doe example |
|---|---|---|
| After a round | Thanks, one line at most about the conversation, then ask about next steps. No recap of the call. | "Hi Sam, thanks for the time today. I enjoyed it. What are the next steps from here? Jane" |
| A thank-you after a call | The same day. Thanks, one specific thing from the call, and anything you said you would send. No recap, no new asks. | "Hi Sam, thanks for the call today. It was good to hear that this hire owns the token editor end to end. My portfolio link is below, as promised. Jane" |
| A nudge | One nudge only, after the date they gave has passed. Short, no guilt, no restating your case. Then wait: no second nudge. Put the wait in the tracker's next action. | "Hi Sam, checking in on the hiring manager slots. Happy to work around the team's calendar. Jane" |
| A withdrawal or a decline | Short and warm. Thanks, the decision in one plain line, and an open door. No reasons beyond one true line, no other company named. After the user sends it, the tracker status becomes `Withdrawn`. | "Hi Pat, thank you for the time you and the team have given me. I've decided to withdraw from the Senior Product Designer process. I'd be glad to stay in touch, and I hope our paths cross again. Jane" |
| A check-in | Urgency without exact dates. Mention other processes only if true, and only if already in "What you have told them" or added there now. | "Hi Pat, I'm moving forward in a couple of other processes, and I'd like to keep Northwind in the mix. Is there an update on next steps? Thanks, Jane" |
| A reply to a rejection | Brief thanks and an open door. Nothing more. | "Hi Pat, thanks for letting me know, and for your team's time. I'd be glad to stay in touch if a design-systems role opens up. Jane" |
| A confirmation | A statement, not a question. | Before: "Would Tuesday at 2 pm work for you?" (they already offered it). After: "Tuesday 20 Oct at 2:00 pm ET works. See you then." |

Check the weekday and time zone of every date with a command before it goes in (hard rule 17).

### 3.9 Referrals, hiring posts, and going back to a company

**Asking for a referral:**

1. Referrals are scarce. Rank the company's open roles first, and ask for the best one.
2. Ask a contact to refer the user only for roles in the contact's own team.
3. If the user needs sponsorship, check the role's sponsorship line first.
4. Ask the contact how they submit. Often one résumé goes in for all roles.
5. Never cold-apply to a role someone is referring the user for.
6. A referrer holds a snapshot of the user's story. If the story changes materially, tell the referrer and offer the updated file.

**Answering a hiring post:**

1. Apply first. Then draft a note to the person who posted, saying the user applied.
2. If the post says "email me", draft an email, not a LinkedIn message.
3. Draft notes only to people in the user's target job market.
4. A connection note stays under the platform's character limit (read the limit shown in the box) and reads as an invitation. The user sends it (hard rules 1 and 2).

Jane Doe example, after applying: "Hi Robin, I saw your post about the design-systems role on your team and applied this morning. I led the consolidation of Figma's design system across 12 product teams. Happy to share more if useful. Jane"

**Going back to a company** after the user declined, or was declined: draft a note to the warmest person the user met there, and ask which role fits before applying again.

## 4. The three moves: claim it, say nothing, disclose only hard gates

A disclaimer nobody asked for is a gift to the reader's doubt. There are three moves, not two:

1. **Claim it**, when it is true.
2. **Say nothing**, when it is not true and nobody asked. This is the move most often missed.
3. **Disclose it**, only for a hard gate (sponsorship, location, travel, a pay floor, a start date). Even then, **lead with the yes**.

Phrases that signal a confession is coming, and should almost never appear: "to be honest", "I'll be straight with you", "I want to be upfront", "unfortunately", "while I don't have", and an answer that opens with "None" or "No".

| Before | After | The move |
|---|---|---|
| "Do you have AI product experience?" "None directly, I want to be upfront about that." | "Two things carry over. I designed Linear's command palette, which is the same problem as a prompt box: one input, a thousand intents. And I've run a design system across 12 product teams." | Claim it. Lead with what is true. |
| "…but I haven't owned a design-token pipeline end to end." (nobody asked) | (sentence deleted) | Say nothing. |
| "Can you travel 40% of the time?" "Not really, I can't do more than 25%." | "I can travel up to a quarter of the time, and I'm in Brooklyn for anything in New York." | Disclose a hard gate. Lead with the yes. |
| "Your design system runs at a scale I've only touched the edge of." | "I've run a design system across 12 product teams, and I want to take that further." | Never compliment them by shrinking the user. |
| (A user who needs sponsorship) "Not without sponsorship." | "I'm authorized to work in the US now, on <visa type from profile.md>. A new employer would need to sponsor a transfer." | Disclose a hard gate. Lead with the yes. Facts only from `profile.md`. |

## 5. Plain English

If a shorter, common word does the same job, the long one is decoration. Cut it. The reader is judging how clearly the user explains things, and reaching for a long word sounds like performing instead of explaining.

**Never strip a real technical term.** Design tokens, component library, WCAG, RAG, SQL: these are the substance and they stay. The rule kills fancy abstract words, not the vocabulary of the user's field.

| Do not write | Write |
|---|---|
| leverage | use |
| utilize | use |
| facilitate | run, or help |
| spearheaded | led |
| synergy | working together (or cut it) |
| provenance | where it came from |
| assertion | claim |
| ground a claim | back it up |
| operationalize | put into practice, or run |
| holistic | whole, or end to end |
| drove cross-functional alignment | got design, product and engineering to agree |
| non-technical stakeholders | people who don't write code |
| do triage | sort through |
| the surface was simple | it looked simple |
| robust | solid (or say what makes it solid) |
| in order to | to |

## 6. No em dashes, and why

**The rule:** no em dashes in anything that goes out in the user's name: résumés, cover letters, emails, LinkedIn messages, form answers, portfolio text, and invisible text such as image alt text and page titles. Use a plain hyphen, a colon, or two sentences.

**Why:**

- Many readers, and some screening tools, now treat the em dash as a sign of AI-written text. Some companies screen applications for exactly that. One dash can make the user's real words look generated.
- Most people never type one. Their keyboard has no key for it. A letter full of them does not sound like the user.

**The check** (the `printf` builds the em dash, so the command itself contains none):

```bash
grep -n "$(printf '\342\200\224')" cover-letter.md                            # a markdown or text draft
pdftotext JaneDoe_Resume.pdf - | grep -n "$(printf '\342\200\224')"           # a PDF, if pdftotext is installed
```

Both must print nothing. Check the PDF, not only the markdown it came from.

## 7. Never expand a name beyond the source

An email address is not a name. A rejection from `pat@northwind.com`, signed "Pat", supports "Pat" and nothing else.

- Write "Pat", or "Pat (pat@northwind.com)". Never "Pat Lee", never "Patricia".
- The same goes for job titles, company names, and anything else where a fragment invites completion.
- Chat is not a lower standard than a file. The same rule applies when Hope tells the user something in chat.

## 8. Checklist before handing over a draft

Run every item. Fix what fails, then hand it over.

- [ ] It answers the question that was asked.
- [ ] The whole thread was read, including what the user last sent, and read again just now.
- [ ] Nothing contradicts "What you have told them" in the role's `APPLICATION-ANSWERS.md`.
- [ ] Peer, not desperate: not a second follow-up, no timeline asked twice, no next call proposed for them, no pay plans in writing.
- [ ] Dictated phrasing was rewritten in the document's register.
- [ ] Every day, date and time was checked with a command and is in the user's time zone.
- [ ] Every number, date, name and title is traced to the canon, `career.json`, `profile.md`, or the user's words in chat.
- [ ] Every duration was computed with a command (lesson 14).
- [ ] Nothing was added because the posting named it (P3).
- [ ] No sentence exists only to flatter the company. No mirrored posting language.
- [ ] The best line is not the first line. Nothing comes after the strongest ending.
- [ ] Every vague amount is a number, date or scale from the canon, or the user was asked.
- [ ] Nothing is framed modestly that could be stated as fact.
- [ ] Any awkward adjacent fact is stated, not left out.
- [ ] No self-undermining sentences. Hard gates lead with the yes. Run `grep -niE "to be honest|be straight|upfront|unfortunately|I don't have|I haven't" <file>` and justify every hit.
- [ ] A "what are you like" answer leads with a preference, not a number.
- [ ] A "why us" answer is about the user, and never mentions pay.
- [ ] A cover letter has the fixed shape, one sentence of company relevance, no practical-notes paragraph, and about 300 to 360 words.
- [ ] Two live letters at one company differ only in paragraph 1, and the exclusivity grep prints nothing.
- [ ] Nothing re-asks a question the form already asks.
- [ ] Semicolons are full stops: `grep -n ";" <file>` prints nothing in the message text.
- [ ] The plain-English table (section 5) was applied.
- [ ] The em dash check prints nothing, in the PDF too.
- [ ] No name is expanded beyond its source.
- [ ] No client names and no internal project names.
- [ ] The draft header is there, with the `Role:` line first and "Status: draft only. <Name> sends." (shape in `references/hunt-folder.md`, section 5.5).
- [ ] It passes the read-aloud test.

## 9. How Hope learns from an edit

Every edit the user makes to a draft is a lesson about how they write. Hope records it, so the next draft needs fewer edits.

**When:** the user edits a draft file, pastes a version they rewrote, or sends something different from the draft (seen read-only in their Sent folder).

1. **Get both versions as files.** Hope's draft is already a file. Save the user's final version word for word in the same folder as `sent-<what>-<YYYY-MM-DD>.md`, for example `sent-email-pat-2026-10-14.md` (the record is what the user sent; see `references/hunt-folder.md`, section 5.5).
2. **Compare them word by word.** This works outside a git repository. Exit code `1` just means the files differ.

```bash
git diff --no-index --word-diff email-draft-pat-2026-10-14.md sent-email-pat-2026-10-14.md
```

3. **Name the pattern behind each change**, in one line each: what Hope wrote, what the user wrote, the rule. Group changes that share a rule. Example: "Hope quoted Northwind's values back at them. Jane deleted the sentence. Rule: never quote a company to show you read the page."
4. **Read `applications/_common/my-voice.md`, "Patterns Hope learned".**
   - Pattern already there: add this example under it, and note that Hope repeated it.
   - Pattern not there: append a new dated entry with the before, the after, and the rule.
5. **If the user rewrote most of the text themselves**, also add their version to "Samples", word for word. Their own writing is the best target there is.
6. **If an edit corrected a fact** (a number, a title, a date), write it to the canon in `HUNT-PROTOCOL.md` the same turn. If it set a standing instruction, write it under "My rules".
7. **Tell the user in one line.** Example: "Learned from your edit: you cut the line praising Northwind. Added to my-voice.md."

Do not over-learn. A change is a pattern only if it would change the next draft too. A one-off fact goes to the canon, not to `my-voice.md`. Never argue an edit back. The user's version wins.
